# Reference Sources: Where to Go Look, By Need

Vocabulary comes from seeing, not from remembering. When a direction is unclear
— or when the first idea is suspiciously familiar — the move is to name **two
or three specific places to look and what to look at in each**, not to browse a
gallery hoping for inspiration.

The transfer rule from the main skill applies without exception: **extract the
principle, never the identity.** If a viewer could name the site you looked at,
you copied the identity. Note the *mechanism* — how the shape solves the job,
what the rhythm is, where the emphasis sits — then rebuild it in this product's
own material.

## How to use this file

- Match the **need**, not the industry. A gym site and a fintech dashboard can
  share a routing pattern; a gym site and another gym site usually share only
  clichés.
- Look at **three** examples, not thirty. Name what each does differently for
  the same job — that difference is the vocabulary you were missing.
- Bring back a **shape and a mechanism**, described in words, before opening a
  design tool. "Register rows with the meta right-aligned and a hairline
  between, image only on hover" is usable. "Something like that site" is not.
- Sources rot. If a name here is dead or has changed character, say so rather
  than pretending; the categories below outlive any particular site.

## By need

### Section composition — how others solve this section's job
- **Land-book**, **SiteInspire** — landing pages and sites, filterable by type
  and style. Best for seeing many solutions to the same job in one sitting.
- **Mobbin** — large library of real product screens and flows, searchable by
  pattern. Strongest source for app and product UI rather than marketing pages.
- **Awwwards**, **Godly** — the ambitious end. Useful for range, dangerous as a
  default: much of it optimises for jury attention rather than for a reader
  deciding whether to hire someone.
- **Minimal.gallery**, **Httpster** — the restrained end; good counterweight to
  the above.

### Motion — what the effect actually looks like in use
- **Codrops** — demos plus write-ups plus source, organised by technique. The
  closest thing to a curated pattern library for web motion; strongest single
  source for "what could this section do instead of sitting still".
- **Motion (motion.dev)** examples — the library's own gallery, useful for
  seeing what a given API buys you before adopting it.
- **Awwwards** motion filters — range, with the same caveat as above.
- **Rive community files** — what authored interactive vector animation can do
  when a designer, not a developer, drives it.
- **Emil Kowalski's writing and course** — the taste layer for interface motion:
  when animation earns its place, and the small decisions that separate polished
  from noisy. The local `emil-design-eng` skill carries this philosophy; load it
  when the task is interface polish or animation judgement.

### Typography — pairings and display type in real use
- **Typewolf** — pairings in context, with the fonts named.
- **Fonts In Use** — type in real-world projects, indexed by industry and format.

### Interaction and flow — how a multi-step task is actually staged
- **Pageflows**, **Screenlane** — recorded flows through real products.
- **Mobbin** — flows as screen sequences.

### Craft principles rather than examples
- **Refactoring UI** — why a layout reads the way it does; principles that
  survive restyling.
- **Laws of UX** — the cognitive principles behind pattern choices, useful for
  arguing a decision rather than asserting taste.

### The product's own world (the highest-yield source, and the most skipped)
Not a website at all. Every domain has physical artifacts and visual
traditions — technical drawings, ledgers, timetables, packaging, forms,
signage, maps, instrument panels. These are where designs no one else ships
come from, because competitors are all looking at the same galleries. Search
the trade's own material: archives, manuals, catalogues, museum collections.
See [aesthetic-derivation.md](aesthetic-derivation.md) for the transfer method.

## Offering a look, in practice

When proposing directions, name the destination and the question, and offer to
go and capture it rather than describing from memory:

> For the "routes to other pages" section, three worth a look: an editorial
> index register (how the meta column and the hairlines do the work a card
> would), a list-with-preview (what happens to the layout when the preview is
> empty), and a relational map (whether the connections are real or decorative).
> Want me to pull live examples of each and lay them out side by side?

If a capture tool is available in the environment, use it: fetch the pages,
screenshot the relevant sections, and present them as a small comparison board
with one line each on the mechanism. A named board beats a list of links,
because the point is to build vocabulary — and vocabulary needs to be seen next
to its alternatives, not one tab at a time.

Keep captures out of the deliverable unless they are cleared for it: references
inform the work, they do not appear in it.
